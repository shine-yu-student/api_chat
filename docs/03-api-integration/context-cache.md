# 上下文前缀缓存利用策略（Context Cache）

> 定义如何最大化 DeepSeek 自动硬盘缓存的命中率，以及长对话的截断降级策略。
> 依据：[官方「上下文硬盘缓存」文档](https://api-docs.deepseek.com/zh-cn/guides/kv_cache)（2026-07 核实）。

## 1. 机制要点（官方）

- 缓存**自动开启、自动管理**：`prompt_cache_key` / `prompt_cache_retention` 不支持，无需也无法手动配置。
- 缓存是**前缀匹配**：每次请求的用户输入结束位置与模型输出结束位置会产生「缓存前缀单元」；系统还会识别公共前缀落盘；长输入按固定 token 间隔落盘。
- **完整匹配缓存前缀单元才能命中**：请求 A+B 后请求 A+C 不命中（B≠C），但系统会把公共前缀 A 落盘，第三次 A+D 可命中 A。
- 命中情况：`usage.input_tokens_details.cached_tokens`（Responses API 格式）= 命中 token 数；`input_tokens` 为总输入。
- 「尽力而为」：不保证 100% 命中；缓存构建秒级；闲置几小时~几天自动清空。
- 缓存只影响输入计费，不影响输出质量与随机性。

**对应用的推论：客户端的全部优化手段 = 让每次请求的输入前缀尽量一致。**

## 2. 请求前缀结构（本应用）

```
[instructions（System Prompt 快照）] + [历史 messages 1..n] + [本次用户消息]
```

`instructions` = 会话的 System Prompt 内容**快照**（FR-11，见 prompt-library.md），**恒定位于最前**。空会话（未锁定）不产生任何请求；首条消息发送时快照冻结，此后永不变。

## 3. 前缀稳定性规则（必须遵守）

| # | 规则 | 原因 |
|---|---|---|
| 1 | 会话内 `instructions`（= System Prompt 快照）内容**恒不变**：对话开始前选定，首条消息发送时冻结；库条目的后续编辑/删除不影响已开始会话 | 快照任何变化 → 整个前缀失效；本规则由 FR-11 锁定机制强制保证 |
| 2 | 会话内当前路径的消息严格按时间序追加，**不改写、不重排、不删除中间消息**（分支切换不改变任何分支自己的消息顺序） | 任何中间变化都破坏前缀 |
| 2b | **分支（FR-12）**：编辑/重新生成创建新分支后，新分支从分支点起成为新前缀——分支点之前仍命中缓存，分支点之后重新构建；同一分支路径内保持稳定 | 分支是「新增前缀」而非「修改历史」，缓存规则不受破坏 |
| 3 | 每条 user/assistant 消息的 content 在发送后**冻结**（UI 上不可编辑历史；本应用不支持编辑/重发替换历史） | 同上 |
| 4 | reasoning item 默认**不回传**（见 thinking.md）——回传也是固定序列，但多传无收益 | 减少传输量，且保持与官方推荐的「无工具轮不回传」一致 |
| 5 | `web_search_call` item 按原 id 稳定回传 | 官方要求，且顺序固定 |
| 6 | 截断只能「从最旧开始丢弃」，且一次截断后保持新前缀稳定（见第 5 节） | 前缀匹配特性 |
| 7 | 不把时间戳/随机内容拼进 instructions 或历史消息 | 每次变化 → 全部未命中 |
| 8 | 并发发送多条消息（本应用禁止）会打乱顺序 → UI 上发送中禁止再次发送 | 保序 |

## 4. 命中率观测与展示（FR-7 验收）

每次 `response.completed` 后从 `usage` 计算并展示：

```ts
const cached = usage.input_tokens_details.cached_tokens;
const total = usage.input_tokens;
const hitRate = total > 0 ? cached / total : 0;
```

UI：助手消息底部用量行（小字）：
`⚡ 输入 1,234 tokens（缓存命中 89%）· 输出 567 · 思考 300`

- 多轮对话连续提问时命中率应稳定高（官方机制：第二轮起命中第一轮前缀单元 + 公共前缀落盘后更优）。
- 若连续多轮命中率持续为 0，排查是否违反第 3 节规则（尤其是 instructions 抖动、历史被改写）。

## 5. 长对话截断降级策略

上下文窗口 1M tokens；超过会 400（`truncation` 不支持）。预算策略：

1. **预估**：实现轻量 token 估算（中文 ≈ 0.6~0.8 token/字 或直接用字符数×系数保守估算，精度不需要高，留 30% 余量），每轮发送前估算 input 总长度：
   - `预估 = instructions + 全部历史 + 本次输入`
2. **截断规则**（触发时）：
   - 保留 `instructions` 与**最近 N 轮**完整消息（含其 reasoning 标记、web_search callId）；
   - 丢弃最旧的完整轮次（user+assistant 成对丢弃，**绝不拆半轮**，否则 web_search_call/reasoning 与消息失配）；
   - 直到预估 ≤ 预算（默认 700K tokens，可配）；
   - 截断后 UI 提示「上下文过长，已省略最早的 X 轮对话」。
3. **截断后**：新前缀从截断点开始稳定，缓存会重新构建（官方：请求结束位置落盘 + 间隔落盘），后续轮次重新享受命中。
4. **截断与缓存的关系**：截断牺牲一次前缀（旧前缀不再复用），但避免 400 且后续命中恢复——这是唯一可用的降级路径，不要试图「从中间压缩历史」。

> 实现提示：截断是纯函数（`truncateHistory(history, budgetTokens)`），单测覆盖：成对丢弃、不拆 web_search 轮、预算边界。

## 6. 多会话与缓存

- 每个会话独立前缀（不同 instructions/历史），互不影响。
- 切换会话后第一轮未命中属正常（该会话前缀尚未落盘或已过期），连续对话后恢复。
- 同一浏览器多标签页操作同一会话会互相覆盖前缀（本应用不处理多标签同步，属范围外）。

## 7. 成本示例（参考官方价格，deepseek-v4-flash）

| 场景 | 输入（未命中 1 元/百万） | 输入（命中 0.02 元/百万） |
|---|---|---|
| 10K token 历史，每轮新增 200 token，命中率 95% | 10K×1 元 = 0.01 元 | 200×1 + 9.8K×0.02 ≈ 0.000396 元 |

命中率对成本影响约 50 倍，前缀稳定性是本应用最重要的成本控制点。
